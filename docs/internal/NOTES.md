# NOTES — lessons from this implementation session

- **Clone-bug attribution in docs/internal/DATA-COLLECTION.md was wrong.** Git blame puts the `source.id` ReferenceError in `dcb4d21` (Jul 26, deployed Aug 6), not `42bf56a`. Mattered because re-examining `dcb4d21` surfaced a second latent bug (auth.js's removed `safeError` import) that the wrong attribution would have hidden.
- **The Aug 6 deploy changed no per-item bulk execution code** (byte-identical loops before/after) — so the bulk failure bursts are pre-existing modes made newly visible, not regressions. Full write-up: docs/incident-2026-08-06-deploy.md. Mattered because it stopped a wrong "roll back the deploy" instinct.
- **durationMs-per-item discriminates bulk failure mechanisms**: ~0.3–0.5 s/item = fast-fail 404 resubmission; ~1–1.5 s = token-refresh failure; ~3.5+ s = 429-retry exhaustion. The Aug 6–8 unfollow/unlike bursts ran at ~0.3–0.4 s/item (404 signature); the bulk-like trains at ~4.7 s/item (quota signature).
- **Cache invalidation had to move after logging but stay in the same synchronous tick as `res.json`** — deferring it to a later tick would let the client's immediate refetch read a stale cache. The reorder is safe only because no `await` sits between the response and the invalidate call.
- **Jest needs dummy SoundCloud env vars in this sandbox** (`soundcloud-client.js` constructs at import and throws without them). With them, the suite is green — the "1 failed suite" was environmental, not a code failure.
- **Prisma BigInt columns return JS `BigInt` values**: `res.json` throws without a `BigInt.prototype.toJSON` patch (added in server/index.js), and `Set.has(bigint)` silently misses number members — every comparison boundary needs `Number()` (api.js followback check, growth-scheduler, excludedTargetIds).
- **`status: 'partial'` already had a writer** (followed-playlist-clone) before growth-reverse was moved onto it — so giving 'partial' a real dashboard state fixed two actions at once.
- **User.soundcloudId and OperationLog.soundcloudId stay Int deliberately.** They hold SC *user* IDs (max observed well under int32); widening them touches session/auth serialization and admin allowlist comparisons — not worth the blast radius yet. GrowthAction.targetId was different because 'like' rows store *track* IDs, which already exceed int32.
- **prisma migrate dev can't run in this sandbox** (no database at first), so migration SQL files are hand-written in the repo's existing style; a verifier later applied them to a throwaway Postgres 16 and DDL-diffed against `prisma db push` output — byte-identical. Empirically executing the exact SQL beat inspection: it caught nothing here but proved the ON CONFLICT dedupe requirement and the `ANY(array)` parameter serialization that inspection could only assume.
- **A truthiness check against a plain object is not a whitelist**: `CATALOG_SORTS[userInput] ? ...` let `?sort=constructor` through via the prototype chain into `Prisma.raw` (syntax-error 500, not injection — but still non-whitelist text in a raw fragment). `Object.hasOwn` is the check. Mattered because the same pattern reads naturally and passes review.
- **getReposts coerces missing titles to the string 'Unknown'** — harvesting those rows would have written 'Unknown' as a *resolved* catalog title that enrichment never revisits. Sanitize at the harvest boundary, not in the catalog: sources own their quirks.
- **prisma/migrations/migration_lock.toml still says `provider = "sqlite"`** and the 2025 init migration is SQLite DDL, so the migrations directory as a whole cannot replay via `prisma migrate deploy` against Postgres — the project effectively runs on `db push`. Pre-existing, not from this branch; matters for anyone assuming migrate-based deploys work.
- **A supertest assertion can be answered by a process that is not under test, and it looks like a flaky test.** `supertest/lib/test.js:63` calls `app.listen(0)`, which binds the *wildcard* address (`::`/`0.0.0.0`), and then requests `127.0.0.1:<port>`. Those are different addresses and macOS lets them coexist: if any other process on the machine already holds that port on `127.0.0.1` specifically, the wildcard bind **succeeds** — no `EADDRINUSE` — and the request is answered by the other process. Reproduced exactly (hold a port on 127.0.0.1 → bind the same port on the wildcard → request 127.0.0.1:port → the foreign server answers). That is the explanation for `tests/routes/admin-feedback.test.js` once failing with the body `"auth required\n"`, a string that exists nowhere in this repo, its history or `node_modules`. It presents as a rare, unreproducible, different-test-each-time failure, because it needs the OS to hand `listen(0)` a port some unrelated local service is already holding on loopback (this machine currently has several, e.g. `127.0.0.1:9932` and `Ollama` on `127.0.0.1:49510`, both in or near the ephemeral range). **The obvious fix does not work**: passing a host to `listen` (`listen(0, '127.0.0.1')`) makes the bind asynchronous — Node routes it through a DNS lookup even for an IP literal — so `server.address()` returns `null` immediately afterwards, which is precisely what supertest reads synchronously on the next line. Patching it that way makes every supertest suite fail and hang; verified, then reverted. A real fix has to change supertest itself (bind loopback and await `listening`) or run the suite where no other process holds loopback ephemeral ports. Until then, treat a backend failure whose response body does not appear anywhere in the repo as this, not as a bug in the test. **Second confirmed instance, and it does not fit that heuristic**: `tests/routes/playlist-keyword-search.test.js › rejects more than 200 track removals` intermittently gets **200 where it expects 400** — no foreign body, nothing unrecognisable, just a status that looks like a validator regression. `curl -X POST http://127.0.0.1:49510/api/playlists/tracks/bulk-remove` against the Ollama listener returns exactly that 200. So the tell is not only a strange body: **any** assertion that a route *rejects* something can be satisfied-in-reverse by a foreign process that accepts everything. Before believing such a failure, re-run the file alone; it passes, because the port lottery is per-run.
