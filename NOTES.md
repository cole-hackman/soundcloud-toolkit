# NOTES — lessons from this implementation session

- **Clone-bug attribution in DATA-COLLECTION.md was wrong.** Git blame puts the `source.id` ReferenceError in `dcb4d21` (Jul 26, deployed Aug 6), not `42bf56a`. Mattered because re-examining `dcb4d21` surfaced a second latent bug (auth.js's removed `safeError` import) that the wrong attribution would have hidden.
- **The Aug 6 deploy changed no per-item bulk execution code** (byte-identical loops before/after) — so the bulk failure bursts are pre-existing modes made newly visible, not regressions. Full write-up: docs/incident-2026-08-06-deploy.md. Mattered because it stopped a wrong "roll back the deploy" instinct.
- **durationMs-per-item discriminates bulk failure mechanisms**: ~0.3–0.5 s/item = fast-fail 404 resubmission; ~1–1.5 s = token-refresh failure; ~3.5+ s = 429-retry exhaustion. The Aug 6–8 unfollow/unlike bursts ran at ~0.3–0.4 s/item (404 signature); the bulk-like trains at ~4.7 s/item (quota signature).
- **Cache invalidation had to move after logging but stay in the same synchronous tick as `res.json`** — deferring it to a later tick would let the client's immediate refetch read a stale cache. The reorder is safe only because no `await` sits between the response and the invalidate call.
- **Jest needs dummy SoundCloud env vars in this sandbox** (`soundcloud-client.js` constructs at import and throws without them). With them, the suite is green — the "1 failed suite" was environmental, not a code failure.
- **Prisma BigInt columns return JS `BigInt` values**: `res.json` throws without a `BigInt.prototype.toJSON` patch (added in server/index.js), and `Set.has(bigint)` silently misses number members — every comparison boundary needs `Number()` (api.js followback check, growth-scheduler, excludedTargetIds).
- **`status: 'partial'` already had a writer** (followed-playlist-clone) before growth-reverse was moved onto it — so giving 'partial' a real dashboard state fixed two actions at once.
- **User.soundcloudId and OperationLog.soundcloudId stay Int deliberately.** They hold SC *user* IDs (max observed well under int32); widening them touches session/auth serialization and admin allowlist comparisons — not worth the blast radius yet. GrowthAction.targetId was different because 'like' rows store *track* IDs, which already exceed int32.
- **prisma migrate dev can't run in this sandbox** (no database), so migration SQL files are hand-written in the repo's existing style and validated by inspection; `prisma generate` + the Jest suite validate the schema and client code compile together.
